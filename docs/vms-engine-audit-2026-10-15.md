# Rust VMS 엔진 점검과 운영 기능 — v0.5.0

소스와 기존 실행 시험을 기준으로 점검했다. 이번 변경은 기존 Rust 서비스의
운영 확장이며, 원본 uVMS 바이너리를 추가 분석하거나 원본 내부 알고리즘을
복원했다는 의미가 아니다. Java는 변경하지 않는다.

## 점검 결과

| VMS 역할 | 현행 상태 |
|---|---|
| 카메라 수집·다중 시청 | RTSP/TCP, 카메라 alias별 공유 입력, WebRTC/MSE/HLS/RTSP 재송출 |
| 음성 | AAC·G.711·Opus 입력 및 출력별 공유 변환 |
| 수동·예약 녹화 | SQLite에 의도 유지, MP4 분할, 원자적 파일 공개, 재연결 |
| 검색·재생·다운로드 | 카메라/시간 검색, HTTP Range, 기존 웹 녹화 재생 |
| 녹화 구간·공백 | **이번 추가:** 실제 파일을 대조하는 구간 API |
| 장애·복구 이력 | **이번 추가:** 입력·녹화·설정·서비스 상태 전환의 영속 저널 |
| 운영 상태 | **이번 추가:** DB 읽기, 파일시스템 여유, 녹화 의도/실제 상태, 세션 슬롯, 이력 유실 |
| 비정상 종료 흔적 | **이번 추가:** 이전 정상 종료 미확인 이력, 시작 시 발견한 partial 수와 보존 이력 |
| 저장 정책 | 기존 전역 용량 제한과 초과 시 정지 유지. 자동 삭제·순환 덮어쓰기 없음 |
| 장치 관리 | 환경변수/설정 파일 기반. ONVIF 검색·프로파일 조회·PTZ·실행 중 카메라 CRUD 없음 |
| 영상 이벤트 | 움직임·가림·객체 감지, 이벤트 전후 녹화 없음. 이번 저널은 영상 분석 이벤트가 아님 |
| 연속 재생 | RAM DVR 및 개별 녹화 재생 지원. 날짜를 넘는 녹화 연속 재생·다중 카메라 동기 재생은 없음 |
| 추가 입력·출력 | RTMP·브라우저 송출·SRT·MKV/ASF 없음. 현재 우선 범위는 RTSP 관제 |
| GPU | NVIDIA 직접 경로 컴파일됨. 실제 GPU 실행 검증은 아직 없음 |
| 이중화 | 프로세스 재시작 복구 지원. 서버 간 failover·복제·다중 저장소 없음 |
| 사용자 권한 | 사용자 요구대로 추가하지 않음. 카메라 자체 인증만 사용 |

장치 제어·영상 분석·이중화까지 완성된 범용 상용 VMS로 주장하지 않는다.
ONVIF/PTZ는 실제 장비의 capability·프로파일·동작을 확인하며 확장할 별도 영역이다.
기존 HLS/MSE의 짧은 음성 미검출 표본과 다일 연속 운전 미검증 한계는
[1시간 시험 보고서](surveillance-soak-2026-10-15.md)에 그대로 남아 있다.

## 운영 상태 API

- `GET /healthz`: 기존 프로세스 생존 확인. 카메라 장애에도 HTTP 200일 수 있다.
- `GET /api/status`: 상세 상태 JSON, 응답 가능하면 HTTP 200.
- `GET /readyz`: 같은 JSON. 운영 조건이 충족되면 200, 그렇지 않으면 503.

운영 조건은 DB의 controls 테이블 읽기 성공, 이력의 마지막 쓰기 실패 없음,
파일시스템의 프로세스 사용 가능 공간 1 MiB 이상, 현재 녹화가 요청된 모든
카메라의 상태가 `recording`인 것이다. 예약 시간이 시작되어 연결 중인 동안도
503이 된다. 대기 중인 카메라를 검사 목적으로 접속하지 않는다.
`input_active`는 현재 입력 세션 상태이며, 미사용 카메라의 false는 고장이 아니다.
이 API는 시청자 브라우저의 디코딩/소리 출력이나 모든 카메라의 물리적 건강을
보증하지 않는다. 디스크 여유 조회는 Linux statvfs이며 쓰기 시험은 하지 않는다.
저장 장치의 잠복 오류나 쓰기 권한 변경까지 예측하는 검사는 아니다.

`storage.used_bytes`는 기존 녹화 예산 회계로, 완료/미완료 파일과 예약된 쓰기를
포함한다. `limit_bytes`는 설정 예산이고 `filesystem_available_bytes`는 실제
파일시스템 여유라 서로 다르다. SQLite DB는 녹화 예산에 포함하지 않는다.
`unfinished_files_at_startup`은 마지막 시작 시 발견한 수이며 실시간 partial 수가 아니다.
이 파일들은 삭제·수리·공개하지 않는다. 이미 쓰던 파일 수동 정리 후 사용량을
갱신하려면 서비스 재시작이 필요하다.

`sessions.occupied_slots`는 기존 WebRTC/MSE/RTSP 제한 슬롯 사용량이다.
HLS HTTP 클라이언트 수, 녹화 작업 수, 카메라 수로 해석하지 않는다.

## 영속 운영 이력

`GET /api/events?after_id=0&limit=200&stream=camera`

`stream`은 선택 사항이다. ID 오름차순으로 최대 1,000개를 반환한다.
응답의 `next_after_id`를 다음 조회의 `after_id`로 넘긴다. 카메라 필터를
사용하면 서비스 전체 이벤트는 제외된다. `time_ms`는 Unix milliseconds다.
ID는 재시작 후에도 유지되며 같은 밀리초/시계 보정에도 페이지 순서를 유지한다.

| kind | state 예시 |
|---|---|
| input | connecting, online, unavailable, interrupted, format_changed, idle, stopped |
| recording | connecting, recording, retrying, storage_full, off, scheduled, stopped |
| recording_control | on, off, auto — 성공한 의도 저장 뒤 기록 |
| service | started, stopped, previous_shutdown_unconfirmed |
| archive | unfinished_file_preserved |

`online`은 최초 영상 수신, `idle`은 소비자 없는 정상 유휴 정리다.
원인 미확인 단절을 인증 오류나 카메라 고장으로 추정하지 않는다.
오류 원문·RTSP URL·비밀번호는 이벤트 payload에 넣지 않는다.
`previous_shutdown_unconfirmed`는 직전 서비스 저널의 정상 종료 기록을 찾지
못했다는 의미다. SIGKILL 외에 이력 유실도 가능하므로 전원 장애라고 단정하지 않는다.

최근 10,000개만 보존한다. 이는 **이력 행 보관 한도**이며 영상 자동 삭제가 아니다.
오래된 커서에는 `cursor_expired=true`와 `oldest_id`를 반환한다. 초기 조회
`after_id=0`은 현재 보관분을 읽는다. 장기 감사 기록이 필요하면 외부에서 수집해야 한다.

영상 처리에서는 용량 256의 채널에 넣고 DB를 기다리지 않는다. 별도 작업이
최대 64개씩 SQLite transaction으로 저장한다. 큐 초과·DB 저장 실패 시
`journal.lost_events`에 해당 프로세스의 유실 수를 표시한다. 마지막 DB 저장이
실패하면 `write_failed=true`이며 다음 성공 때 false로 돌아온다. 유실 수는
다음 성공으로 지우지 않지만 프로세스 재시작 때 초기화된다. 장애 중에도
무손실 감사를 보장하는 저널은 아니다. 정상 종료에는 큐를 비우되 최대 10초로 제한한다.

## 녹화 구간·공백

`GET /api/timeline/camera?from=1792000000000&to=1792003600000`

`from`, `to`는 필수 Unix milliseconds이고 `[from,to)` 반개방 구간이다.
최대 31일, 후보 10,000개까지다. 초과하면 부분 결과를 완전한 결과처럼
내보내지 않고 413으로 거절한다. 시간을 좁혀 조회한다. 오래된 길이 미확인
녹화도 후보로 포함되므로 그러한 파일이 매우 많으면 좁은 구간도 제한될 수 있다.

- `recorded`: 존재하는 파일의 겹침/인접 구간을 합친 목록.
- `gaps`: 요청 범위에서 검증된 완료 녹화가 없는 구간.
- `recorded_ms`, `gap_ms`: 합은 정확히 요청 구간 길이.
- `completed_clips`: 반영한 완료 파일 수.
- `unavailable_clips`: 없거나 크기가 다르거나 안전한 일반 파일이 아닌 후보 수.
- `unknown_duration_clips`: 존재하지만 종료 시각을 확정하지 못한 후보 수.

DB 색인과 파일 존재/크기를 대조하며, 카메라 디렉터리 및 파일 symlink는
반영하지 않는다. 미확정 길이 파일은 보관하면서 커버리지에는 넣지 않는다.
GET은 파일을 수정하거나 삭제하지 않는다. 완료 후 같은 크기로 외부 변조한
파일까지 검출하는 해시 검사나 미디어 디코딩 검사는 아니다.

`includes_active_recording=false`: 쓰는 중인 세그먼트는 완료 후 나타난다.
따라서 현재 시각 직전의 공백이 곧 장애라는 뜻은 아니다. 시작 전·수동 중지·
예약 밖 시간도 공백이다. 장애 판단에는 운영 이력/녹화 의도를 함께 사용한다.
이번 API를 기존 웹 타임라인 화면으로 새로 연결하지는 않았다.

## 검증

`scripts/verify-vms-operations.py`는 합성 RTSP 4개와 별도 `uvms-soak*`
서비스만 사용한다. FFmpeg는 합성 카메라 생성, ffprobe는 테스트 검증 도구이며
Rust 서비스에서 실행하지 않는다. 시험 데이터와 요약은
`test-results/vms-operations/result.json` 및 동명 JSON 보고서에 기록한다.

단위 시험은 이력 보관 한도/커서/재시작/큐 초과/DB 오류, DB 없는 상태의
읽기 전용 점검, 구간 병합/파일 누락/크기 변경/길이 미확인/조회 제한을 다룬다.
실행 시험은 실제 4개 녹화, 단절·복구, SIGKILL 후 기존 MP4·partial 보존,
상태와 이력, 파일 누락 시 커버리지 제외, 정상 재시작 및 전체 완료 MP4 디코딩을 다룬다.

### 실행 결과

- Rust 단위 시험 39개 통과, 1개 벤치마크 제외, Clippy 경고 0.
- 합성 카메라 4개 운영 시험 69.332초 통과. 이번 신규 기능의 집중 장애 시험이며
  이전 버전의 1시간 시험을 새 버전의 장시간 결과로 다시 세지 않았다.
- 입력 복구 후 4개 녹화/ready 복귀 1.943초(이 실행의 관측값).
- SIGKILL 전 완료 MP4 10개와 미완료 파일 4개 내용 보존, 자동 녹화 재개.
- 완료 MP4 18개 전체 H.264 영상·AAC 음성 프레임 디코딩 검사 통과.
- 1MiB 공유 한도 별도 시험: MP4 4개, 총 1,041,944 bytes, 재시작 전후 불변,
  4개 모두 디코딩 통과. 한도 초과 ready 503과 storage_full 이력 확인.
- 배포 시 기존 서비스의 녹화 225개와 설정 파일 hash 보존 확인.
- 배포 서비스에는 기존 256MiB 녹화 한도가 차 있어 ready 503을 반환한다.
  이는 실제 파일시스템 부족이 아닌 설정 한도이며, 기존 설정/파일을 유지했다.

수치와 바이너리 SHA256은 [기계 판독 보고서](vms-engine-audit-2026-10-15.json)에 있다.
