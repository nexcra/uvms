# Rust v0.4.3 동시 접속 측정

이 문서는 동일 PC에서 진행한 실제 부하 측정과 그 한계를 기록한다.
대역폭 나눗셈으로 산출한 이론값을 검증된 최대 시청자 수로 사용하지 않는다.

## 조건과 판정

- Ryzen 7 PRO 5750GE, 8코어/16스레드, 호스트 RAM 약 64GB.
- 서버는 Ubuntu 24.04 WSL, 수신 브라우저는 Windows Edge headless.
- 합성 H.264 640×360, 설정 15fps, 수신 영상 약 1.24Mbps, 음성 없음.
- 동일 camera alias를 여러 연결이 구독하며 녹화는 비활성화.
- 운영 바이너리와 동일한 SHA-256
  `73492572ee633567f197df43aa29b4a879a6f52d36e0b63f4df22d29e77e0fb1`.
- 테스트 서비스만 HTTP8091 / UDP50800 / max_sessions=1024로 실행.
  운영 서비스 HTTP8080의 max_sessions=32는 변경하지 않음.
- 이 PC에서는 다른 Java 프로세스 등도 CPU를 사용하고 있었다. 128개
  브라우저 시험 중 호스트 전체 CPU 100%를 관찰했다. 다른 작업을 중지하지 않았다.
- 1Gbps 물리 NIC가 있으나 이 시험의 로컬/WSL 경로는 외부 NIC 처리량 검증이 아니다.

브라우저 시험은 각 단계에서 준비 5초 뒤 60초를 측정한다. 독립된
RTCPeerConnection마다 실제 `<video>`로 디코딩하며 canvas는 사용하지 않는다.
페이지당 8개 연결이며 여러 브라우저 프로세스로 분산할 수 있다. HLS 캐시는
10초마다 playlist를 요청해 유지한다. 운영 UI의 다른 처리는 실행하지 않는다.

통과 기준은 **모든 연결**이 connected, 640×360, 구간 평균 13fps 이상,
패킷 손실 비율 0.1% 이하, 평균 jitter buffer 대기 250ms 이하이며 10초 구간의
프레임 진행 정지가 없는 것이다. 짧은 freeze는 별도로 기록하므로 이 기준의
통과가 무끊김 재생이나 종단 지연 보장을 의미하지 않는다.
CPU는 해당 프로세스의 **한 코어=100%** 기준이다.

## 실제 브라우저 디코딩

| 조건 | 연결 | 평균/최저 fps | 서버 CPU | 서버 최대 RSS | 수신 합계 | 결과 |
|---|---:|---:|---:|---:|---:|---|
| 단일 브라우저, 기본 디코딩 | 32 | 14.50 / 14.49 | 33.47% | 94.38MiB | 39.59Mbps | 통과 |
| 단일 브라우저, 기본 디코딩 | 64 | 5.31 / 4.95 | 64.57% | 150.22MiB | 79.23Mbps | 실패 |
| 단일 브라우저, 가속 디코딩 비활성 옵션 | 32 | 14.49 / 14.40 | 31.15% | 94.49MiB | 39.68Mbps | 통과 |
| 단일 브라우저, 가속 디코딩 비활성 옵션 | 64 | 13.76 / 12.83 | 60.99% | 150.45MiB | 79.55Mbps | 실패 |
| 브라우저당 32개, 가속 디코딩 비활성 옵션 | 64 | 14.34 / 14.16 | 61.75% | 140.82MiB | 79.27Mbps | 통과 |
| 브라우저당 32개, 가속 디코딩 비활성 옵션 | 128 | 11.48 / 9.21 | 155.02% | 217.49MiB | 158.95Mbps | 실패 |

모든 위 구간에서 RTP packetsLost 증가량은 0, 서버 입력 RTSP 연결은 최대
1개였다. 64개 분산 실행의 browser CPU는 281.04%, 128개는 499.18%였다.
64개 통과 구간에도 브라우저 freezeCount 증가량의 합이 327회 있었고,
128개 구간에는 3,087회였다. 평균 fps만으로 완벽한 품질을 주장하지 않는다.

단일 브라우저의 기본 디코딩 64개에서는 일부 연결의 totalDecodeTime 증가량을
framesDecoded 증가량으로 나눈 값이 프레임당 약 200ms였다. 가속 디코딩
비활성 옵션에서는 약 2ms 수준이었지만, 부하와 구성도 달라 이것만으로 특정
GPU 드라이버의 결함을 단정할 수 없다. decoderImplementation 통계가 제공되지
않아 실제 디코더 구현명은 미확인이다.

비활성 옵션은 Chromium의
[`--disable-accelerated-video-decode`](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/public/common/content_switches.cc)
이며 원시 결과의 `softwareDecode`는 이 옵션의 요청 여부를 뜻한다.

## 전송 전용 수신 검증

`examples/rtc_capacity.rs`는 독립된 ICE·DTLS·SRTP 연결을 만들고 복호화한
H.264 RTP payload를 수신한다. 연속 sequence number와 marker로 끝난 프레임을
세며, 각 연결의 프레임률 13 이상·sequence 불연속 0·10초 구간 정지 0을
통과 기준으로 사용한다. 패킷 재정렬도 불연속으로 센다.

**H.264 디코딩·화면 출력·실제 브라우저 호환성 시험은 아니다.** 서버와 수신기
모두 WSL에서 실행하므로 물리 NIC·인터넷 회선도 검증하지 않는다. 이 시험은
HLS 캐시를 계속 갱신하지 않는다. 브라우저 시험과 직접 성능 비교하지 않는다.

| 연결 | 최저 RTP 프레임률 | 서버 CPU | 서버 최대 RSS | payload 합계 | 결과 |
|---|---:|---:|---:|---:|---|
| 32 | 15.00fps | 19.52% | 77.00MiB | 40.99Mbps | 통과 |
| 64 | 15.00fps | 35.88% | 119.78MiB | 82.00Mbps | 통과 |
| 128 | 15.00fps | 92.75% | 200.68MiB | 164.02Mbps | 통과 |
| 256 | 14.99fps | 101.28% | 364.03MiB | 327.99Mbps | 통과 |
| 512 (별도 120초) | 14.99fps | 252.55% | 685.92MiB | 656.57Mbps | 통과 |

32~256개는 60초 측정, sequence 불연속과 구간 수신 정지 0이었다. 각 단계는
같은 서버 프로세스에 연결을 누적해서 측정했다. 256개 시점의 별도 프로세스
소켓 확인에서도 입력 RTSP 1개, 미디어 UDP50800 1개를 확인했다. mDNS5353
소켓은 연결별로 존재하므로 서버 전체 UDP 소켓이 1개라는 뜻은 아니다.

512개는 서버를 재시작한 뒤 16개씩 연결을 추가하고 약 120초 유지했다.
512개 모두 connected, sequence 불연속과 구간 수신 정지 0이었다.
수신기 CPU는 161.51%, 최대 RSS는 178.17MiB였다. 별도 소켓 표본에서도
입력 RTSP 1개와 미디어 UDP50800 1개, mDNS5353 소켓 512개를 확인했다.

## 해석과 미확인 범위

현재 근거로 말할 수 있는 범위는 **브라우저 디코딩 64개가 정한 기준 통과,
전송 전용 512개가 2분간 통과**이다. 64개에도 짧은 freeze가 있었으며,
128개 브라우저 시험은 다른 작업과 함께 호스트 CPU가 포화된 상태에서
기준을 충족하지 못했다. 128개가 Rust 서버의 한계라는 결론은 근거가 없다.

512개는 시험한 전송 연결 수의 최대일 뿐, 서비스의 최대 수용량이나 512명
브라우저 재생 보증이 아니다. 분리된 여러 부하 발생 PC와 실제 송신 NIC를
통한 반복·장시간 시험이 필요하다. 3Mbps/1080p, 음성, 여러 독립 카메라,
녹화 병행, H.265 변환, TURN 중계, WAN 손실 환경의 최대치는 이번에 측정하지
않았다. 기존 대역폭 계산(1Gbps의 80% / 3Mbps ≈ 266)은 이론값으로 남는다.

이번 변경은 부하 도구와 보고서이며 운영 미디어 엔진·Java 코드는 변경하지
않았다. 운영 서비스의 32개 접속 상한도 유지했다.

## 재현 및 증거

`scripts/rust-optimization-fixture.py /opt/uvms/uvms-gateway`를
`UVMS_BENCH_MAX_SESSIONS=1024`와 함께 WSL root에서 실행한다.

브라우저: Windows에서 `node scripts/benchmark-capacity.mjs`.
환경변수는 `UVMS_CAP_COUNTS=32,64,128,256`, `UVMS_CAP_SECONDS=60`,
`UVMS_CAP_BROWSER_PEERS=32`, `UVMS_CAP_SOFTWARE_DECODE=1`,
`UVMS_CAP_OUTPUT=test-results/capacity/<run>`이다. 기본은 브라우저 하나이며,
가속 비활성 옵션도 기본 적용하지 않는다.

전송: WSL에서 `cargo build --release --example rtc_capacity`로 빌드하고
동일 `UVMS_CAP_COUNTS`, `UVMS_CAP_SECONDS`를 지정해 실행한다.
`UVMS_CAP_OUTPUT`은 디렉터리가 아니라 결과 JSON 파일 경로이다.
`UVMS_CAP_RAMP`는 한 번에 협상할 연결 수이며 기본 4, 허용 범위 1~32이다.
끝나면 `systemctl stop uvms-rust-opt-bench`로 테스트 서비스만 중지한다.

원시 자료는 Git 제외 경로 `test-results/capacity/`에 남겼다.

- `step-2/`: 기본 브라우저 측정.
- `software-decode/`: 단일 브라우저의 가속 비활성 옵션 측정.
- `browser-pool/`: 브라우저당 32개 분산 측정.
- `transport.json`: 전송 전용 수신 측정.
- `transport-512.json`: 별도 512개 전송 지속 측정.
- `transport-256-service.jsonl`: 256개 시점의 입력 연결·UDP 소켓 확인.
- `transport-512-service.jsonl`: 512개 시점의 입력 연결·UDP 소켓 확인.
- `host.json`, `environment.json`: 장비, 설정 상한, 바이너리 동일성.
- `step-1/`, `harness-check/`: 초기 가상 페이지의 로컬 네트워크 접근 차단 기록.
  실제 서버 navigation으로 수정한 뒤 `harness-check-2/`에서 1개 재생을 검증했다.
  초기 차단은 서버 용량 실패로 계산하지 않는다.
