# 원본 추가 분석과 Java 이식 — 2026-10-14

이번 변경은 원본 함수의 호출·버퍼·소켓 경로를 추가 분석한 뒤 Java에 적용했다. 원본 전체 알고리즘이나 Windows IOCP를 그대로 복제했다고 주장하지 않는다. 분석 보고서는 `original-shared-udp.md`, `original-buffer-optimizations.md`이며 함수 주소·Evidence ID·확인되지 않은 범위를 포함한다.

## 확인한 원본과 적용 경계

| 원본에서 확인한 구조 | Java에 반영한 동작 |
|---|---|
| 공용 포트 하나에 소켓 16개와 IOCP 워커 16개. 최초 ufrag 조회, 이후 발신 IP:port 조회 | Linux SO_REUSEPORT로 공용 포트 하나에 고정 소켓 풀 16개. 서비스가 소켓을 소유하고 종료된 피어만 등록 해제. 피어별 송신 소켓을 순환 배정 |
| EXE가 candidate를 변경하고 내부 DLL 주소로 UDP 릴레이 | Java가 직접 ICE/DTLS/SRTP를 처리하므로 내부 릴레이 소켓·홉을 생략 |
| 릴레이의 최초 분배는 STUN cookie/ufrag 문자열 탐색, 실제 ICE 인증은 downstream | Java는 구조화된 USERNAME과 HMAC을 검증한 뒤 endpoint 등록. 다른 살아 있는 피어의 endpoint를 빼앗지 못함 |
| 압축 프레임 공통 큐는 참조계수로 공유. RTC NAL 정규화 결과를 소비자 순회에서 한 번 생성·재사용 | 공유 Frame에 NAL offset/length를 보관. 각 시청자의 RTP는 개별 NAL/FU 중간 배열 없이 최종 RTP 배열에 복사 |
| MSE adapter는 출력 크기를 먼저 계산하고 capacity를 재사용 | Java 비동기 전송의 버퍼 수명을 지키며 정확한 최종 크기로 할당. MSE/mdat 중첩 복사 제거. 불변 전송 버퍼를 전송 중 재사용하지 않음 |
| 제한 모드 큐는 오래된 항목 축소 후 keyframe gate를 다시 적용 | 실시간 구독은 큐 전체를 비운 뒤 다음 IDR부터 재개. 원본이 마지막 항목 하나를 남기는 동작과는 다름. 녹화 구독은 넘칠 때 오류 유지 |

SRTP 출력 배열에 직접 암호화하고 HMAC을 나누어 갱신한 변경, H.264 slice header를 필요한 만큼만 읽는 변경은 Java 자체의 할당 최적화다. 이를 원본 네이티브 암호 구현을 복제한 것으로 설명하지 않는다. RTP sequence·SSRC·암호 키·재전송 이력은 피어별로 분리한다.

## 측정 조건

실제 카메라가 측정 중 H.264 트랙을 제공하지 않게 되어 해당 시험은 제외했다(`before/`). 사용자 선택에 따라 기존 로컬 테스트 영상으로 비교했다. 카메라 설정은 변경하지 않았다.

- 같은 Windows/WSL2 Ubuntu 24.04 호스트, 논리 CPU 16개, OpenJDK 21, Xms64m/Xmx512m.
- 로컬 testsrc2 H.264 Baseline 640×360, 설정 15fps, 실제 WebRTC 수신 약 13~14fps, 시청자당 약 1.16Mbps.
- FFmpeg는 별도 테스트 영상 생성 서비스에만 사용. 측정 대상 Java 서비스는 FFmpeg·ffprobe 접근을 차단하며 자식 미디어 프로세스를 실행하지 않는다.
- 같은 Edge 독립 페이지 16개, WebRTC와 MSE를 순서대로 측정. 각 버전 JVM 재시작 후 각 방식 15초 예열 시험, 정식 시험은 준비 5초 후 25초. 별도 benchmark 서비스 HTTP8090/RTSP8560 사용.
- CPU100%는 논리 코어 하나. RSS는 JVM 전체 프로세스이며 GC·JIT·앞 단계 할당 영향을 포함한다. 이 짧은 시험은 최대 수용량·장기 안정성·언어 전체 성능 비교가 아니다.
- 원본 Windows 서버 성능은 이번에 측정하지 않았다. 이전 실제 1080p 카메라의 Rust/Java 결과와 입력 조건이 다르므로 직접 비교하지 않는다.

## 결과

| 방식 | 변경 전 CPU | 변경 후 CPU | 상대 감소 | 전 / 후 RSS MiB | 전 / 후 평균 FPS |
|---|---:|---:|---:|---:|---:|
| webrtc | 12.31% | 9.07% | 26.3% | 229.9 / 234.0 | 13.51 / 13.51 |
| mse | 9.58% | 7.27% | 24.2% | 230.7 / 224.9 | 10.09 / 10.14 |

수신 payload 합계는 WebRTC 전/후 18.52/18.49Mbps, MSE 18.65/18.60Mbps로 비슷했다. WebRTC RTP 손실은 전후 모두 0이었다. MSE에는 전후 모두 브라우저 렌더링 누락이 관측됐으며 평균 표시 FPS는 약10이었다. 이 수치를 서버 RTP 손실로 해석하지 않는다.

메모리는 WebRTC에서 약4.1MiB 늘고 MSE에서 약5.8MiB 줄었다. 전체 메모리가 일관되게 감소했다고 볼 수 없다. RSS에는 커널 소켓 버퍼가 포함되지 않는다. 프로세스 GC/JIT·배경 부하를 완전히 통제한 장기 통계가 아닌 단기 관측이다.

검증: 단위 테스트11개, 고정 암호 벡터6개(RTP rollover와 SRTCP), 16브라우저/2별칭 공용 포트, 8명 종료 후 나머지 재생과 8명 재접속, pre-offer 종료80회, MSE pause/continue/switch, RTSP16명 각100프레임, MP4 2초30프레임 녹화·다운로드 일치·종료 후 partial0개를 통과했다. 배포된 8088에서도 16뷰어 공유 포트 시험을 통과했다.

Linux 서비스 배포 JAR SHA-256: `04ed9860cb434f37c46480eb15ace8e7c9c27e883775334f38e96e622cb4deef`, 크기13,140,354bytes(13.14MB). 운영 공용 포트50200에 고정 소켓16개가 확인됐고, 테스트 인스턴스는 종료했다. 카메라 설정·환경변수 파일 해시는 배포 전후 동일하다. 원본 Rust 서비스는 계속 active 상태다.


중간의 단일 Java 소켓 실험도 `fixture-single-socket/`에 남겼다. 공용 포트 하나와 OS 소켓 하나는 다른 개념이다. 단일 소켓 측정에서 CPU 증가가 관측되어 원본처럼 같은 공용 포트의 고정 소켓 풀을 구현해 추가 검증했다. 단일 소켓 송신 경합은 검토한 가설이며 프로파일러로 원인을 확정한 것은 아니다.

## 배포와 재현

최종 서비스는 HTTP8088/RTSP8558이며 공용 WebRTC UDP 포트는 기본 50200이다. 기본 소켓/수신 워커 수는 16, 선택 설정 `ice_udp_workers`는 1~16이다. 기존 `ice_udp_max`는 호환용으로 무시한다. 소켓 수는 시청자 수에 따라 증가하지 않는다. 세션 인증 토큰은 추가하지 않았으며 카메라 입력에만 원래 자격 증명을 사용한다.

`scripts/java-optimization-fixture.py <JAR 절대 경로>`는 기존 테스트 RTSP 입력에 연결하는 별도 서비스만 만든다. `benchmark-viewers.mjs`에서 URL8090, 서비스명 uvms-java-opt-bench, 폭640/높이360, 입력 포트8554를 지정하면 재현할 수 있다. `java-shared-port-regression.mjs`는 두 카메라 별칭의 16뷰어 공유 포트·8명 종료·8명 재접속을 검증한다. 두 별칭은 같은 합성 입력을 각각 연결하며 실제 카메라 두 대를 시험한 것은 아니다.

지원 범위는 계속 H.264 영상 전용이다. 원본 libwebrtc의 전체 혼잡 제어·pacing·FEC·오디오·H.265·TURN을 이번 작업에서 추가한 것은 아니다.
