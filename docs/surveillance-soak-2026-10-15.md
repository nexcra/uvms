# Rust 다중 카메라·녹화·장애 복구 시험

## 범위와 조건

운영 Rust v0.4.3을 먼저 검사하고, 발견한 문제를 수정한 v0.4.4 Linux 실행 파일을
별도 서비스에서 다시 검증한다.
Java 구현·서비스, 실제 카메라와 운영 녹화 설정은 변경하지 않는다.
독립된 합성 RTSP 입력 4개는 H.264 640×360/15fps 영상과 각각 AAC,
PCMU, PCMA, Opus 음성을 사용한다. FFmpeg는 합성 송출기에만 사용하며
미디어 서비스에서는 실행할 수 없다. 녹화 검사는 외부 시험 도구인 ffprobe로 한다.

Windows Edge의 실제 4분할 화면을 WebRTC·WebSocket MSE·HLS 세 페이지에서
동시에 실행한다. 합계 12개 재생과 카메라 4대의 MP4 녹화를 유지한다.
AAC·PCMU는 수동 녹화, PCMA·Opus는 한 번 실행하는 예약 녹화다.
MP4 목표 구간은 15초, 전체 저장 한도는 8GiB이고 기존 파일을 삭제하지 않는다.
HLS는 2초 조각·30초 창·카메라별 8MiB 한도·15초 유휴 해제를 사용한다.

별도 포트는 HTTP 8099, RTSP 재송출 18575, 공용 WebRTC UDP 51900,
합성 RTSP 18574, 장애 주입 프록시 18576이다. 데이터는 실행마다 새
`/var/lib/uvms-soak/recordings-<run>` 폴더에 쓴다.

## 장애와 판정

본시험 목표는 1시간이며 다음을 순서대로 주입한다.

- AAC 카메라 송출 목표 30초 중지 후 다시 시작.
- PCMU의 TCP 연결은 유지한 채 양방향 데이터를 목표 40초 폐기해 무응답 연결 재현.
- 합성 RTSP 서버 재시작으로 입력 4개 동시 단절.
- Rust 시험 서비스 정상 재시작. 수동·예약 녹화 의도와 완료 파일 색인 유지 검사.
- AAC 카메라 송출 목표 20초 중지·재시작을 5회 반복.
- 마지막에는 재생과 녹화를 중지한 뒤 HLS·RTSP 입력·UDP 세션 자원 회수 검사.

시험은 화면 새로고침이나 재연결 버튼을 대신 눌러 주지 않는다. 기존 플레이어의
자동 복구를 관찰한다. 장애 대상 카메라에만 복구 유예 75초를 적용하며,
다른 카메라는 계속 검사한다. 연결 복원부터 영상·음성이 있는 두 연속 표본까지의
관측 시간을 보고하고, 카메라 촬영부터 출력까지의 종단 지연으로 부르지 않는다.
주입 제어도 표본 주기로 실행하므로 실제 중단 길이는 목표보다 길 수 있으며,
실제 중단·복원 시각을 집계에 사용한다.

표본마다 디코딩 프레임 증가, 화면 상태·해상도, 실제 음성 RMS를 검사한다.
음성은 표본당 100ms 간격의 5개 분석 창을 사용한다. 약 5초 대기와 표본 수집
시간이 합쳐져 실제 관측 주기는 약 6.5초다. 한 번의 짧은 버퍼 부족과 지속
장애를 구분하기 위해, 5fps 미만·비정상 화면·음성 미검출 표본이 10초 이상
이어지면 실패로 처리한다. 짧은 저하도 원시 자료와 집계에서 숨기지 않는다.
따라서 통과가 모든 순간의 무손실·무음 구간 0·완벽한 15fps를 뜻하지 않는다.

녹화는 상태뿐 아니라 최신 완료 파일 시각이 진행하는지 확인한다(45초 한도).
종료 후 모든 MP4를 디코딩 검사하고 H.264 첫 키프레임, 영상·음성 DTS의
단조 증가, 파일 크기와 SQLite 색인 일치, 미완료 파일, 페이지 나누기 검색과
Range 다운로드 바이트 일치를 확인한다.
파일 내부 DTS 공백이 250ms를 넘거나, 주입 장애 밖에서 완료 파일 사이에
2초를 넘는 공백이 생기면 실패로 처리한다. 더 짧은 차이는 RTP 시계와
파일 생성 시각의 차이를 포함하므로 무조건 유실 프레임으로 해석하지 않는다.

CPU·RSS·스레드·파일 디스크립터·입력 연결·UDP 포트를 1초마다 기록한다.
CPU는 한 코어=100%이며 브라우저·합성 송출기 CPU는 포함하지 않는다.
서버와 브라우저는 같은 PC의 Windows/WSL에서 동작한다. 다른 작업이 실행되는
환경이므로 이 결과는 최대 성능 측정이나 전용 서버의 용량 보증이 아니다.

## 확인한 문제와 수정

### 파일 확정 지연이 녹화 수신을 막는 문제

첫 1시간 시험에서는 재생의 지속 장애는 없었지만, 939개 파일 전체 검사에서
장애 주입 밖의 2초 초과 공백 3곳과 음성 샘플이 없는 짧은 파일 1개가 나왔다.
해당 시험은 통과로 처리하지 않았다. Opus 녹화 중단 로그도 같은 시점에 남았다.

녹화 루프는 `sync_all()`과 SQLite 등록을 기다리는 동안 영상·음성 broadcast를
읽지 않았다. 영상 채널은 32프레임이므로, 디스크 확정이 몇 초 늦으면 버퍼를
초과해 녹화가 재시도됐다. 다음 파일의 시작 시각도 지연된 파일 생성 시각으로
잡혀 실제 수신 시점보다 늦게 기록됐다.

별도 재현 시험에서 완료 파일의 첫 `fsync` 네 번을 각각 5초 늦췄다.
수정 전 네 카메라 모두 녹화가 중단됐고 약 5초의 공백 8곳과 음성 샘플이 없는
짧은 파일 4개가 재현됐다. 같은 지연을 넣은 수정본에서는 녹화 중단·기준 초과
공백·음성 샘플 없는 파일이 모두 0건이었고 완료 파일 16개를 검사했다.
처음 시험의 개별 지연 원인을 사후에 모두 단정할
수는 없지만, 이 저장 대기 경로의 결함은 통제된 조건에서 확인했다.

수정본은 녹화 수신과 디스크 쓰기를 분리한다. 큐는 카메라별 1,024개 표본과
16MiB의 보관 예산으로 제한하고 압축 프레임의 `Arc`를 공유한다. 일반 시청자용
broadcast 크기는 늘리지 않는다. 소스 종료 시 이미 수신한 표본을 처리하고,
녹화 종료 시 수신 작업을 해제한다. 새 파일 시각은 파일 생성이 끝난 시각 대신
수신 큐에 들어온 영상의 시각을 사용한다. 제한을 넘는 장기 저장 지연은 무한히
메모리를 늘려 감추지 않고 기존 실패·재시도 경로로 처리한다.

단위 시험은 쓰기가 멈춘 동안 영상 240개와 음성 480개를 전송해 기존 수신자의
`Lagged`와 새 수신 큐의 순서·표본 보존을 비교한다. 별도 시험으로 큐의 바이트
한도와 종료 시 구독 해제도 검사한다.

### 녹화가 쌓인 서비스의 기동 지연

v0.4.3 시험에서 서비스 재시작 후 준비 로그까지 약 64초가 걸렸다.
`record::start()`는 완료 파일마다 MP4 box를 다시 읽어 길이를 계산한 뒤
SQLite에 삽입을 시도했다. 이미 정확한 색인이 있는 경우에도 파일 분석을
먼저 수행했고, 그 뒤 `ON CONFLICT`가 기존 행을 유지했다.

v0.4.4는 카메라별 정확한 색인의 파일명·크기를 한 번 읽는다. 디스크 파일
크기가 일치하면 MP4 재분석을 생략한다. 새 파일·추정 메타데이터는 기존
가져오기 경로를 유지한다. 전체 파일 크기 합산은 생략하지 않아 저장 한도는
그대로 적용된다. 완료 파일이 변경되지 않는 기존 저장 계약을 이용한 최적화며,
매번 파일 내용을 검증하는 무결성 검사로 부르지 않는다.

동일한 완료 녹화의 하드링크와 SQLite 복제본으로 전후 기동을 비교하고,
정확한 색인 보존·용량 합산·색인 한 행을 제거한 파일의 재가져오기를 검사한다.
기존 파일 내용은 전후 SHA-256으로 확인한다.

264개·658,854,235바이트의 같은 녹화에서 v0.4.3의 HTTP 준비는 51.456초,
최종 v0.4.4는 0.052초였다. 색인 한 행을 지운 경우도 0.347초에 해당 파일을
다시 등록했다. 기동 시간은 프로세스 실행부터 HTTP health 응답까지이며
50ms 재시도 간격과 로컬 환경의 영향을 포함하는 단일 비교다.

별도 4대 동시 녹화·1MiB 저장 한도 시험에서는 한도 이하에서 모두 정지했고,
정지 상태 6초와 재기동 후 6초 동안 완료 파일 크기·해시가 유지됐다.
4개 파일 모두 영상·음성 디코딩이 가능했다. 이는 저장 예산 검사이며
실제 장치의 I/O 오류나 전원 차단에 대한 보증은 아니다.

### 실제 녹화와 다른 화면 표시

다중 화면의 녹화 배지는 실제 `recording` 상태보다 설정의 기본값 `record`를
먼저 확인했다. 기본 녹화가 꺼진 카메라를 API/UI에서 수동으로 녹화하면
파일은 생성되는데 배지는 ‘녹화 꺼짐’으로 표시됐다.

`CameraPlayer.recording()`을 실제 상태 기준으로 바꿨다. `off`, `scheduled`,
`recording`, `connecting`, `retrying`, `storage_full`, `stopped`를 표시한다.
실제 4대 수동 녹화 화면에서 변경 전 실패, 변경 후 성공을 확인했다.

예비 시험에서는 검사기의 오디오 노드 재연결 오류도 발견했다. 이는 서비스
오류가 아니라 시험 코드 문제였다. 같은 HTMLMediaElement에 분석 노드를
중복 생성하지 않도록 수정하고, 단일 순간 RMS 대신 여러 음성 창으로 측정한다.
예비 결과는 최종 통과 결과로 합치지 않고 별도 보존한다.

재시험의 실시간 공백 검사에서도 최신 파일 조회 사이에 완료된 중간 파일을
건너뛰어 공백으로 오인한 사례가 있었다. 전체 파일 검사에서는 해당 구간이
연속됨을 확인했다. 실시간 검사도 의심 구간의 색인을 다시 조회해 실제 인접
파일끼리 비교하도록 수정하고, 그 사례를 재현하는 회귀 검사를 추가했다.

설정한 기준을 통과했다. 상세 값은 [집계 JSON](surveillance-soak-2026-10-15.json)에 있다.

정상 구간의 평균 재생 속도는 WebRTC 14.44fps, MSE 14.17fps, HLS 14.45fps였다.
5fps 미만 표본은 없었다. 다만 RMS가 검출되지 않은 짧은 표본은 WebRTC 0개,
MSE 73개, HLS 54개였다(방식별 정상 구간 표본 1,975개, 카메라별 합계).
10초 이상 이어지는 실패 조건에는 해당하지 않았지만 **짧은 음성 미검출까지
없었다고 해석하면 안 된다.** 이번 계측만으로 브라우저 오디오 출력 지연과
전송·재생 구간의 원인을 분리하지는 못했으며, 해당 표본을 JSON에 남겼다.

RTSP 프록시 포트를 향하는 TCP 연결 관측값은 대부분 4개였다. 정상 구간의
1초 표본 두 개에서는 5개로 관측됐다. 이 계측은 연결별 식별자를 저장하지
않으므로 추가 관측의 원인을 단정하지 않는다. 연결 수의 지속 증가는 없었고
종료 시 모두 해제됐다. ‘모든 순간에 정확히 4개’라고 주장하지 않는다.

| 복원 후 영상·음성 두 연속 표본까지 | 최장 관측 시간 |
| --- | --- |
| WebRTC | 26.448초 |
| WebSocket MSE | 39.491초 |
| HLS | 19.834초 |
| 복원 후 시작된 녹화의 첫 완료 파일 확인 | 19.834초 |

이 시간에는 약 6.5초의 관측 간격이 포함된다. 녹화 완료 확인에는 15초 파일
구간도 포함되므로 녹화 재개 자체가 20초 늦었다는 뜻은 아니다. 플레이어는
연속 실패 시 재시도 간격을 최대 30초까지 늘리는 기존 정책을 유지한다.
의도한 단절·복구 구간에 생긴 녹화 공백 11곳은 별도 기록했다.

## 해석 범위

이 시험은 합성 입력 4대와 실제 브라우저 재생 12개를 사용한 1시간 시험이다.
수일 연속 운전, 실제 카메라 제조사별 RTSP 차이, 물리 회선 혼잡, 최대 시청
가능 인원까지 검증한 결과는 아니다. H.265·NVIDIA GPU 변환과 RTSP 재송출
시청자는 이번 장시간 시험에 포함하지 않았다.

서비스 재시작은 systemd의 정상 종료·기동 경로다. `SIGKILL`, 전원 차단,
디스크 손상 복구는 별도 시험이 필요하다. 의도한 입력 단절 동안의 영상은
녹화할 수 없으므로 해당 공백을 기록하며, 끊긴 구간을 정상 녹화로 세지 않는다.
시험 통과만으로 메모리 누수나 순간적인 프레임 저하가 전혀 없다고 단정하지 않는다.

## 재현과 증거

1. WSL root에서 `python3 scripts/soak-fixture.py setup --binary /opt/uvms/uvms-gateway`.
2. Windows에서 `UVMS_SOAK_SECONDS=3600`, `UVMS_SOAK_OUTPUT=test-results/soak/final`을
   설정하고 `node scripts/soak-surveillance.mjs` 실행. `UVMS_SOAK_FAIL_FAST=1`이면
   운전 중 기준 위반을 발견한 직후 종료해 조사할 수 있다.
3. 시험이 끝나고 같은 fixture를 유지한 상태에서 WSL의
   `python3 scripts/verify-soak-recordings.py <result.json 절대 경로>` 실행.
   과거 파일만 검사할 때는 `--offline`을 쓰며 HTTP 검증으로 간주하지 않는다.
4. `python3 scripts/summarize-soak.py <결과 폴더>`로 집계.
5. `python3 scripts/soak-fixture.py stop`으로 시험 서비스만 정리.

저장 지연 재현은 합성 입력 fixture를 유지한 상태에서
`python3 scripts/verify-recording-disk-wait.py --before <수정 전 Linux 실행 파일>`로
실행한다. 임시 LD_PRELOAD 라이브러리가 이 시험 프로세스의 `.partial` 파일에
대한 첫 `fsync` 네 번만 5초 지연시킨다. 운영 서비스에는 주입하지 않는다.
전후 실행 파일 SHA-256과 녹화 결과를 `disk-wait.json`에 남긴다.

최종 소스는 NVIDIA 기능을 포함한 단위 시험 34개를 통과했다. 별도 성능
마이크로벤치마크 1개는 기본 실행에서 제외된다. Clippy `-D warnings`와 release
빌드도 통과했다. NVIDIA 기능의 빌드 성공이 실제 GPU 변환 검증을 뜻하지 않는다.

원시 자료는 Git 제외 경로 `test-results/soak/`에 둔다. `result.json`은
브라우저·서버 표본, 주입 시각, 실패와 자원 회수 결과를 포함하고,
`recordings.json`은 모든 녹화의 검사 결과와 SHA-256을 포함한다.
시험 녹화·음성·원본 MSI/DLL은 배포하지 않는다.
