# Rust v0.5.1: 실행 중 녹화 한도 변경과 재개

녹화 전역 예산을 변경하는 API를 추가했다. 저장 한도에 걸린 녹화기는
한도 변경 알림을 받으면 현재 녹화 의도와 예약을 다시 확인한다.
서비스 재시작이나 카메라 재등록이 필요 없다. Java와 웹 화면은 변경하지 않았다.

## 사용

```sh
curl http://127.0.0.1:8080/api/storage
curl -X PUT http://127.0.0.1:8080/api/storage \
  -H 'Content-Type: application/json' \
  -d '{"limit_bytes":10737418240}'
```

예시는 10 GiB다. 허용 범위는 1 MiB부터 `i64::MAX` 바이트까지이며,
필수 값 누락·범위 밖 값·알 수 없는 필드는 거절한다. 로그인·토큰은 없고
다른 변경 API와 같은 Origin 검사를 적용한다.

GET 응답:

| 필드 | 의미 |
|---|---|
| used_bytes | 완료/미완료 파일과 진행 중 쓰기 예약을 포함한 전역 사용량 |
| limit_bytes | 실제 적용 중인 한도 |
| remaining_bytes | `max(limit_bytes-used_bytes, 0)` |
| configured_limit_bytes | 시작 시 TOML에서 읽은 기본 한도 |
| automatic_deletion | false — 한도를 줄여도 기존 파일은 삭제하지 않음 |
| restart_required | false |

변경값은 `recording_dir/archive.sqlite`의 settings 테이블에 저장되며,
재시작 때 TOML 기본값보다 우선한다. TOML 값으로 되돌리려면 GET의
`configured_limit_bytes` 값을 PUT하면 된다. 자동으로 설정 파일을 수정하지 않는다.
`/api/status`와 `/api/recordings`도 실제 적용 중인 한도를 반환한다.

PUT 성공은 설정의 저장·반영을 뜻한다. 카메라 연결이나 IDR 수신까지
완료됐다는 뜻은 아니므로 `/api/recording/{stream}` 또는 `/readyz`로 재개를 확인한다.
수동 off나 예약 밖인 카메라를 강제로 켜지 않는다. 같은 값을 다시 PUT해도
한도 대기를 깨워 한 번 재확인한다. 카메라별 할당이 아닌 공유 예산이므로
너무 작은 한도에서는 일부 카메라가 다른 카메라보다 먼저 공간을 사용할 수 있다.

## 데이터 보존과 경쟁 처리

한도와 사용량을 같은 짧은 메모리 잠금으로 처리하여 다중 녹화의 쓰기 예약과
한도 변경이 서로 모순되지 않게 한다. 이 잠금 안에서 파일 I/O나 DB 작업을 하지 않는다.
설정 변경 요청끼리는 별도로 직렬화한다. DB 저장 실패에는 503을 반환하고
실제 한도는 바꾸지 않는다. HTTP 호출자가 연결을 끊어도 이미 시작한 저장·반영
작업은 끝내며, 이 경우 클라이언트는 GET으로 결과를 확인할 수 있다.

사용량보다 낮은 한도로 변경할 수 있다. 이미 존재하는 영상과 변경 전에
예약된 쓰기는 유지한다. 이후 새 쓰기 예약이 거절되고 현재 MP4를 확정한 뒤
`storage_full`로 대기한다. 이 때문에 `used_bytes > limit_bytes`는 가능한 상태다.
상향 후에도 한도에 여유가 없으면 계속 대기하며, 기존 파일을 지우지 않는다.
물리적 디스크 공간을 확보하는 API는 아니므로 실제 파일시스템 여유도 확인해야 한다.

한도 대기 중에도 250ms 간격으로 예약 종료 여부를 확인하도록 수정했다.
이전 버전에서는 예약이 끝나도 설정 변경이나 서비스 재시작까지 `storage_full`에
머물 수 있었다. 이제 녹화 의도가 비활성으로 바뀌면 대기 상태에서 빠져나온다.

사용자가 파일을 외부에서 수동 삭제한 경우의 사용량 재계산은 여전히 재시작이
필요하다. 자동 삭제·순환 녹화·보존 기간·디스크 추가·파일 복구는 이번 범위가 아니다.

## 검증

`scripts/verify-storage-control.py`는 별도 합성 카메라 4대에서 다음을 검사한다.

- 공유 한도 도달 후 같은 PID에서 한도 상향, 녹화/ready 복귀.
- 사용량보다 작은 한도로 축소해도 완료 파일 보존, 새 쓰기 중지.
- 한도 대기 중 예약 종료, 이후 상향해도 수동 off/예약 밖 상태 유지.
- 서비스 재시작 후 한도와 녹화 의도 복원, 완료 파일 hash/사용량 일치.
- 생성된 MP4의 H.264 영상·AAC 음성 프레임 디코딩, 잘못된 요청 거절.

처음 시험에서는 재시작 직후 1~2프레임만 받고 녹화를 끈 파일에 아직 음성
프레임이 없어 검사에 실패했다. 최종 시험은 중지 전 3초 녹화한다. 이는
짧은 녹화에도 반드시 음성이 들어간다는 보장이 아니다. 또한 1 MiB 초기
예산 시험에서 3대가 공간을 선점하는 경우를 관찰해, 4대 재개 시험은
초기 4 MiB로 진행한다. 카메라별 예산 공정성을 추가했다는 의미는 아니다.

단위 시험은 병렬 쓰기 예약/한도 축소/오버플로, DB 저장·복원, 저장 실패 시
미반영 및 Origin 거절을 확인한다. 상세 수치는 `storage-control.json`에 기록한다.

### 2026-10-15 결과

- 단위 시험 41개 통과, 벤치마크 1개 제외, Clippy 경고 0.
- 4대 합성 카메라 집중 시험 31.004초 통과. 한도 상향 후 녹화/ready 복귀
  0.830초 관측. 최대 복구 지연을 보장하는 수치는 아니다.
- 완료 MP4 12개 전체 영상·음성 디코딩 통과, 기존 4개 hash 보존,
  최종 녹화 10,040,187 bytes와 사용량 회계 일치.
- Linux v0.5.1 배포 시 기존 녹화 225개와 설정 파일 hash 보존.
- 실제 서비스 한도를 256 MiB에서 10 GiB로 변경하고, PID 변경 없이
  `camera`, `camera_two` 녹화 재개와 ready HTTP 200 확인.
  `camera_copy`, `camera_live`는 기존 수동 off 상태를 유지했다.
- TOML의 기본 한도 256 MiB는 유지하고 DB에 10 GiB를 저장했다.
  10 GiB에 도달하면 다시 보존 정책에 따라 정지한다. 순환 덮어쓰기는 하지 않는다.

[기계 판독 결과](storage-control.json)에 바이너리 hash와 배포 결과가 있다.
